# BUG-001: Issues: PATCH can set any state, so an issue can be closed without Verify

- **Component:** Issues > Workflow
- **Priority:** P1
- **Found by:** `tests/test_planted_defects.py::test_bug001_...`, SQL check `01_closed_without_verify.sql`, exploratory session 1
- **Build/env:** demo tracker 1.0.0, local SQLite

## Summary
`PATCH /api/issues/{id}` accepts a `state` field and writes it straight to the database. The
dedicated `/transition` endpoint enforces the workflow (Analyze > Integrate > Build > Verify >
Closed, only QA may close), but PATCH bypasses all of it, including the role rule.

## Steps to reproduce
1. Log in as `erin` (engineer) and create an issue (state is `Analyze`).
2. `PATCH /api/issues/{id}` with `{"state": "Closed"}`.
3. `GET /api/issues/{id}`.

## Expected result
HTTP 422, state remains `Analyze`.

## Actual result
HTTP 200, state is `Closed`. History shows `Analyze -> Closed`. The issue never passed Verify and
no QA user signed it off.

## Impact
Breaks the central release-quality rule ("nothing is closed without verification"). Release
readiness numbers become untrustworthy because closed issues can be unverified.

## Suspected cause
`IssueService.update` writes `state` directly instead of calling `transition()`.

## Suggested regression test
Existing strict xfail test. After the fix: remove the PATCH `state` field or route it through
`transition()`, then promote the xfail to a normal test.
